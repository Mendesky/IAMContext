角色 API 更新說明

IAM 新增角色管理 API。查員工權限的結果從此包含角色展開的權限，指派角色開始驗證 roleId。給 console 前端對接用。

一一頁摘要

  1. 新增 9 個端點。8 個在 /roles 底下管理角色（建立、清單、改名、改描述、加減權限、刪除、查角色權限），1 個查「誰持有某角色」。
  2. 3 個既有端點行為改變，形狀不變。GET /employee-access/permissions/{userId}（含 gRPC 同名方法）回傳的權限現在包含角色展開；assign-roles 開始驗證 roleId；permission-holders 現在包含只經角色持有的人。
  3. 唯一的破壞性變更：assign-roles 的 roles 陣列值必須是存在且未刪除的 roleId，否則整包 422 roleNotFound。若 console 目前傳的是自訂角色名稱，切換後會全部失敗。
  4. 不需要重產 client。gRPC proto 沒變；既有 HTTP schema 只有新增（一個端點、一個 query 參數、一個錯誤碼），沒有欄位改名或移除。
  5. 生效時間。角色權限改完，IAM 這端下一個查詢立即反映。經 Middleware 權限快取的其他 context 最多晚 60 秒，與今天直接授權的行為相同。

二認證與共用規則

項目規則
變更類請求（POST、DELETE）Header Authorization: Bearer <IAM_ADMIN_API_TOKEN>。由 AdminTokenMiddleware 把關，token 由 IAM 部署環境提供。
查詢類請求（GET）不需 Bearer token。
操作者所有變更類端點必帶 Header operatorId（字串），寫進事件供稽核。
錯誤回應形狀{ "error": "<錯誤碼>" }。狀態碼只有 404（找不到 aggregate）、422（業務規則或 payload 不合法）、503（KurrentDB 不可用等基礎設施錯誤）。
roleId由 IAM 產生的 UUID 字串，建立角色時在回應取得。角色改名不會改 roleId。
權限 rawValue字串，必須存在於 IAM 的聚合權限目錄（各 context 登錄進來的 permissions.yaml）。加入未知 rawValue 會整批被拒。
Base URL以環境設定為準。本機開發慣用 HTTP 24202。

三新端點

角色的寫入與「查單一角色權限」是強一致：請求成功後立刻可讀。GET /roles 與「角色持有者」走 projection，寫入後約數百毫秒才反映。

POST/roles

operationId createRoleBearer 必要一致性 強一致
// request
{ "name": "審計助理", "description": "審計案件的基本操作權限" }   // description 可省略

// 200
{ "roleId": "6F1C0A3E-3B7E-4B2E-9A0B-2C4D5E6F7A8B" }
錯誤碼狀態觸發
roleNameRequired422name 為空或全空白
roleNameDuplicated422已有同名角色（大小寫敏感、完全比對；盡力檢查，極短時間內的同名並發寫入可能都成功）
invalidPayload422body 不是合法 JSON 或缺必填欄位

GET/roles

operationId getRolesBearer 不需一致性 最終一致
// 200
[
  { "roleId": "6F1C…", "name": "審計助理", "description": "…", "permissions": ["AC.BusinessClient.read", "AC.Case.read"] },
  { "roleId": "9D2B…", "name": "報價主管", "permissions": ["QC.Quotation.approve"] }
]

每筆自帶 permissions，前端可以直接畫「角色 × 權限」矩陣，不必逐一打單角色查詢。順序不保證。projection 未部署或尚無角色時回 []，不是錯誤。

POST/roles/{roleId}/rename

operationId renameRoleBearer 必要一致性 強一致
{ "newName": "審計助理（初階）" }        // 200 → { "roleId": "…" }
錯誤碼狀態觸發
roleNameRequired422newName 為空
roleNameDuplicated422與其他角色同名
roleNameUnchanged422與現名相同
aggregateNotFound404roleId 不存在或已刪除

POST/roles/{roleId}/update-description

operationId updateRoleDescriptionBearer 必要一致性 強一致
{ "newDescription": "…" }               // 可為 null 表示清空；200 → { "roleId": "…" }

錯誤：descriptionUnchanged 422（與現值相同）、aggregateNotFound 404。

POST/roles/{roleId}/add-permissions

operationId addPermissionsBearer 必要一致性 強一致
{ "permissions": ["AC.Case.read", "AC.Case.edit"] }     // 200 → { "roleId": "…" }

批次語意：只記錄「實際新增」的那些。傳進來的全部都已存在時視為無事可做，回 422。

錯誤碼狀態觸發
invalidPermission422任一 rawValue 不在權限目錄中，整批拒絕
permissionsUnchanged422扣掉已有的之後沒有東西可加
aggregateNotFound404roleId 不存在或已刪除

POST/roles/{roleId}/remove-permissions

operationId removePermissionsBearer 必要一致性 強一致
{ "permissions": ["AC.Case.edit"] }                     // 200 → { "roleId": "…" }

只記錄「實際移除」的那些。傳進來的全部都不在角色裡時回 422 permissionsUnchanged。其餘錯誤同上。

DELETE/roles/{roleId}

operationId deleteRoleBearer 必要一致性 強一致
// 200 → { "roleId": "…" }；404 aggregateNotFound：不存在或已刪除
刪除不會被持有者擋下。角色一刪，所有持有者立刻失去這個角色帶來的權限；他們身上殘留的 roleId 變成惰性引用，不報錯。IAM 不提供「刪除前必須先撤銷」的保護，請 console 在刪除前呼叫 GET /employee-access/role-holders?role=… 顯示持有人數並二次確認。

GET/roles/{roleId}/permissions

operationId getRolePermissionsBearer 不需一致性 強一致
// 200
["AC.BusinessClient.read", "AC.Case.read"]              // 404 aggregateNotFound：不存在或已刪除

與 GET /roles 的差別：這條是即時讀 aggregate，寫入後立刻正確；清單那條有 projection 延遲。剛加完權限要立刻顯示時用這條。

GET/employee-access/role-holders?role={roleId}

operationId getRoleHoldersBearer 不需一致性 最終一致
// 200
["userId-1", "userId-2"]           // 無人持有、角色不存在、projection 未部署 → []

回傳的是 userId（與 permission-holders 相同），不是 employeeAccessId。這條掛在 /employee-access 底下，因為持有關係是員工的事實。

四既有端點的變化

GET/employee-access/permissions/{userId}　與 gRPC PermissionsService.getPermissions

回傳形狀不變，仍是權限 rawValue 的字串陣列。內容變成 直接授權 ∪ 該員工每個角色的權限，已去重。已刪除或解析不到的 roleId 貢獻零權限，不報錯。員工不存在的行為不變：HTTP 404，gRPC 回空清單。HTTP 與 gRPC 走同一段程式，結果一致。

同一個權限同時來自直接授權與角色時，任一來源移除都不影響另一來源。同一權限存在於兩個角色時，撤銷其中一個角色後仍有效。

POST/employee-access/{employeeAccessId}/assign-roles

{ "userId": "…", "roles": ["6F1C0A3E-…", "9D2B…"] }     // roles 的值＝roleId
破壞性變更。欄位名仍叫 roles、型別仍是字串陣列，但每個值必須是存在且未刪除的 roleId。任一個查不到，整包回 422 roleNotFound，不寫入任何事件。roleId 請從 GET /roles 或建立角色的回應取得。
錯誤碼狀態觸發
roleNotFound 新增422任一 roleId 在角色目錄中不存在或已刪除
roleAlreadyExists422該員工已持有其中某個 roleId
userIdMismatch422body 的 userId 與該 profile 的 userId 不符
aggregateNotFound404employeeAccessId 不存在

POST/employee-access/{employeeAccessId}/revoke-roles

行為不變，不驗證 roleId 是否仍存在（撤銷一個已刪角色的引用是無害的）。錯誤 roleNotExist 422 的意思是「這位員工身上沒有這個角色」，與上面的 roleNotFound 是兩件事。

GET/employee-access/permission-holders?permission=…&department=…&firm=…

回傳的 userId 清單現在包含只經由角色持有該權限的人。順序：直接持有者在前，保持原順序；經角色持有者排序後接在後面；已去重。department／firm 過濾套用在合併後的結果上。角色反查那一半走 projection，有數百毫秒延遲；projection 未部署時退化成只回直接持有者，不報錯。

五建議的 console 流程

角色管理頁

  1. 進頁 GET /roles，一次拿到名稱、描述與權限集合，可直接畫矩陣。
  2. 建立：POST /roles 取得 roleId，接著 add-permissions。建立後清單約數百毫秒才會出現這個角色；建議用回傳的 roleId 先樂觀加進畫面，或延遲重取。
  3. 編輯權限：以 add-permissions／remove-permissions 送「差集」，不要把整個集合重送。傳全部已存在的東西會得到 422。
  4. 刪除：先 role-holders?role= 顯示持有人數，二次確認後 DELETE。
  5. 權限選單的候選值來源是 IAM 的權限目錄，不要讓使用者自由輸入 rawValue。

員工權限頁

  1. 指派角色：assign-roles 只傳 roleId，選項來自 GET /roles。
  2. 顯示有效權限：GET /employee-access/permissions/{userId}，結果已含角色展開。
  3. 要顯示「某權限是直接給的還是來自哪個角色」：目前沒有專用端點（規劃在後續階段）。過渡做法是前端拿 GET /roles 的 permissions 自行對照該員工持有的角色。
角色權限改完，該角色所有持有者在 IAM 這端立刻生效，不需要對每個人重新指派。但其他 context 若透過 Middleware 的權限快取取權限，最多再等 60 秒。console 若直接打 IAM 的 HTTP 端點，不受這個快取影響。

七相容性與部署

  • 歷史角色字串。過去用 assign-roles 寫進員工身上的非 roleId 字串不會被遷移或清理。它們在查權限時貢獻零權限、不報錯，也不會擋住新的指派。若 console 曾把角色名稱當值送出，需要改成先建角色、再用 roleId。
  • projection 部署。每個環境上線前要跑一次 bash scripts/projection.sh，部署 IAM_GetRoles 與 IAM_RoleHolders 兩支 projection。沒部署時 GET /roles、role-holders 回空陣列，permission-holders 看不到經角色持有的人。
  • gRPC。proto 與產生的 stub 沒變。其他 context 不需改碼，只是回傳內容開始包含角色權限。
  • 狀態。程式在 IAMContext 分支 feat/role-aggregate，全套 103 個整合測試通過，尚未合併主線與部署。
