各 Context 的權限 catalog 要怎麼進 IAM？

核心結論：別問「IAM 要不要 copy 一份」——那是陷阱。要問的是 投影（projection） 還是 fork（copy）。pull / push 只是傳輸細節。

★一眼結論

四點建議，依推薦程度排序。

最推薦
catalog 做成事件流 → IAM 投影成 universe read model。 上游發 PermissionCatalogPublished，IAM 用 projector 投影。你怕的「copy」就變成跟 GetPermissions 同構的 read model——可重建、event log 即 provenance、drift 結構上不可能。
退路
上游發極輕的「我變了」訊號，IAM 收到才 pull 完整 catalog 投影。 上游不想扛發布整包時用。仍是 projection，不是 copy。
注意
每份 catalog 一定要帶 version / content-hash。「是否有更新」靠比 version，不要比對整包；push 幂等、pull 省流量都靠它。
最不推薦
IAM 定時巡所有 context + 自己 copy 一份（你的第一個想法）。 把「列舉所有 context」「逐一 poll」「維護 N 份 fork」三個負擔全塞進 IAM → drift 重現、每多一個 context 就改一次 IAM。

1先拆成兩個正交的軸

你的問句把兩件事黏在一起了。真正決定成敗的是軸 1，不是你問的傳輸方式。

🔑

關鍵是 軸 1：不管 pull 還是 push，只要 IAM「copy 成自有」就會 drift——正是你之前踩過的 IAMC / IAM 那種不報錯、默默授錯權限的 silent divergence。

2軸 1：別 copy-fork，要 derived projection

「copy 一份」的問題不在時機，在 ownership。

正確心智：IAM 持有的是各 context catalog 的「投影」——衍生的、可重建的、帶 provenance（知道從哪來、版本多少）。它不是 IAM 的 authored 內容，只是為了 validate / baseline 維護的 cache。這樣「IAM 裡有一份」是合法的，因為它本質是 derived，不是 fork。

而你正好在 event sourcing / KurrentDB 上 → 投影幾乎免費。

3軸 2：為什麼 push / register 贏過 IAM-poll

不只是時效，是耦合方向。

  • IAM poll：IAM 必須列舉並認識每一個 context、知道各自 endpoint/格式、逐一 diff → 變成耦合到全部 context 的 hub，每多一個 context 就改一次 IAM。
  • context 註冊 / push：IAM 只認識「一個入口」（registry 或事件流）。新 context 自己 register / 發事件 → IAM 一行都不用改。耦合方向對了。

4推薦架構：catalog 即事件流，IAM 投影

跟你現有的 GetPermissions 同構，你會很眼熟。

你怕的「copy」在這裡就變成 universe read model：上游一發布、IAM projector 就更新，allPermissions 那 12 個寫死的假字串被它取代；baseline 再從這個 universe 取子集。沒有手動 copy 步驟 → drift 無從發生。

5別忘了 ownership 的分辨

會進 IAM 的是「vocabulary」；不會進、也輪不到上游定的是「policy」。

東西誰擁有進 IAM？
permission vocabulary
「這些權限字串存在、各代表什麼」		 發布的那個 context 會（投影進來當 universe）
IAM 不可能管理它不知道存在的東西
指派 policy / baseline
「哪個部門/職稱該拿哪些權限」		 IAM 自己 不從上游來
這是 IAM 的 access 決策，別讓上游清單偷渡這層
📌

上游的 catalog 餵的是 IAM baseline 的值域（codomain），不是 baseline 本身。catalog 即使躺在 IAM repo 裡，ownership 永遠是上游的——IAM 只讀、不改它的語意。
