目標

IAMContext 目前沒有「角色」的定義主體——role 只是 EmployeeAccess 上的 Set<String> 字串集合，僅有 assign/revoke 兩個操作，無法建立、查詢、編輯、刪除角色本身。本 task 建立 Role aggregate 作為角色定義的 SSOT，讓管理者能經 UI 在執行期：建立角色（含描述）、改名、批次增減權限、刪除角色，並查詢角色清單、單一角色的權限、以及某角色的持有者（role holders 反查）。這同時為後續「員工有效權限 = 直接授權 ∪ 角色展開」鋪路（該合成不在本 task 範圍，見 Non-goals）。

  • 事件帶 Role 前綴（使用者 2026-08-07 裁決 D14）；因權限操作改批次（D11），原名 RolePermissionAdded 正規化為複數 RolePermissionsAdded / RolePermissionsRemoved。
  • 批次事件記錄「淨效果」：Added 只含實際新增（請求 − 當前）、Removed 只含實際移除（請求 ∩ 當前）——replay 精確、不含 no-op 項。

2. Aggregate（Sources/RoleAggregate/Entity/Role.swift）

package class Role: RoleAggregateProtocol {   // protocol 由 plugin 從 event.yaml 生成 [inferred]
    package let id: String                     // roleId；aggregate 自行生成
    package var metadata: AggregateRootMetadata = .init()
    package var name: String?
    package var description: String?
    package var permissions: Set<String>?
    // category："IAM\(Self.self)" → "IAMRole"
    // → per-aggregate stream "IAMRole-<roleId>"、category stream "$ce-IAMRole"
}
  • roleId 由 aggregate 自行生成（D15）：create 的 convenience init Role(name:description:) 內部 id = UUID().uuidString，client 不供給 id；UUID 碰撞可忽略 ⇒ 不做 create 重複檢查。
  • 不變量：name 非 nil 且非空字串（違反 → roleNameRequired）。
  • 狀態異動只在 when(event:)；命令方法只 validate + apply(event:)。

  • 命名衝突迴避：getPermissions 已被 employee 查詢佔用 → 用 getRolePermissions。
  • 錯誤回應：404（不存在/已刪除）、422（RoleApiError）、503。
  • POST /roles（無 path id）與 DELETE 動詞皆無 repo 先例 inferred；DELETE 的 fallback 為 POST /roles/{roleId}/delete。
  • 守門所有權：POST/DELETE 由 server-level AdminTokenMiddleware 自動守門；GET 放行——本 task 不需、也不得另行設定 per-route 守門。

3b. EmployeeAccessAggregate 側（role holders 反查）

Method / PathoperationId輸入200 回應
GET /employee-access/role-holders?role=<roleId>getRoleHoldersquery role（必填）[String]（userId 清單）
  • 放這裡的理由（D16）：折疊的是 RolesAssigned/RolesRevoked（EmployeeAccess module 內部生成型別）；形狀與 permission-holders 完全鏡像，命名對稱。
  • 無人持有或 role 不存在 → []（不回 404，鏡像 permission-holders）。
  • key 語意：以 EmployeeAccess.roles 儲存的字串原值分流；慣例自本 task 起 assign-roles 應傳 roleId（歷史名稱字串反查不到，已知限制 #3）。

4. 查詢一致性語意

查詢實作路徑一致性空/缺結果行為
getRolePermissionsRoleRepository.find(byId:) rehydrate 自身 stream強一致不存在/已刪除 → 404；無權限 → []
getRolesprojection IAM_GetRolesProjection.js（$ce-IAMRole → linkTo("IAM_GetRoles-all")）+ presenter最終一致無角色 → []；順序不保證
getRoleHoldersprojection IAM_RoleHoldersProjection.js（$ce-IAMEmployeeAccess → per-role linkTo）+ presenter最終一致無人持有 → []；順序不保證

find(byId:) 對已刪除 aggregate 回 nil（DDDKit hiddingDeleted 預設）→ 刪除後查詢自然 404，fail-safe。

5. 錯誤型別（Sources/RoleAggregate/RoleError.swift）

package enum RoleError: Error, Equatable {
    case roleNameRequired       // name 空字串（invariant / create 輸入）
    case roleNameDuplicated     // create/rename：名稱已被使用（best-effort）
    case roleNameUnchanged      // rename no-op
    case descriptionUnchanged   // update-description no-op
    case permissionsUnchanged   // 批次 add/remove 淨效果為空
    case invalidPermission      // 任一權限不在 catalog（整批拒絕）
}

拋出沿用 ContextError<RoleError> factory 慣例。HTTP 映射：RoleError → 422；DDDError.aggregateNotFound → 404；其餘 → 503。

注意：EmployeeAccessError 已有語意相近的 permissionAlreadyExists / roleAlreadyExists 等 case（「該員工已持有該字串」語意）。兩者屬不同 enum、掛在不同泛型特化（ContextError<EmployeeAccessError> vs ContextError<RoleError>）的 extension 上，Swift 型別系統可完全區分，無衝突、不需改名。
no-op 類錯誤（roleNameUnchanged/descriptionUnchanged/permissionsUnchanged）沿用 departmentUnchanged 精神：未變更即拒絕。UI 應把這三種 422 視為良性（畫面已是目標狀態）。

6. 權限合法性驗證（AddPermissions）

  • 批次中每一個 permission 必須 ∈ IAMPermissionCatalog 生成的權限 universe；任一不合法 → invalidPermission，整批原子拒絕。
  • 驗證位置：AddPermissionsUsecase.execute 默認實作（Port/In 層）——aggregate 不依賴 catalog target。
  • inferred 生成符號名與 visibility 需在實作第一步確認；不足時 fallback 見 MD 正本。

7. 角色名稱唯一性（best-effort）

唯一性檢查在 Adapter 層的 CreateRoleApplicationService / RenameRoleApplicationService 做——usecase 只持有 RoleRepository，而查 read model 需要 KurrentDBClient；application service 同時持有兩者，寫入前先查 GetRoles read model。佈線：兩個依賴皆由 ApiHandler 供給（對照 EmployeeAccess 的 ApiHandler(kdbClient:)——以 kdbClient 建構並持有 repository，分別傳給 mutating/query services）；Create/Rename 的 service 只是兩個依賴一起收（init(repository:kdbClient:)），無新機制。同名（大小寫敏感、完全比對；rename 排除自身）→ roleNameDuplicated。read model 最終一致 ⇒ race window（已知限制 #1）；嚴格唯一（reservation）defer。

實作步驟

Step 0：Package.swift + 骨架

  1. 新 target：deps = DDDKit、IAMContextShared、OpenAPIRuntime、IAMPermissionCatalog；plugins = DomainEventGeneratorPlugin、ModelGeneratorPlugin、OpenAPIGenerator。
  2. IAMContextServer、IAMContextTests deps 加 RoleAggregate。
  3. 建 5 個 yaml。
  4. swift build 看 codegen 形狀，確認 PermissionCatalog 生成符號與 visibility（此步允許紅）。

Step 1：Entity 層

  1. Role.swift 三個 init：主 init、Role(name:description:)（生成 UUID().uuidString）、replay 入口。主 init 先直接初始化狀態欄位再 apply(event:)——DDDKit 的 apply 在 when 之前先跑一次 ensureInvariant()，欄位為 nil 會失敗（對照 EmployeeAccess.init 寫法）。
  2. ensureInvariant：name 非空。
  3. 4 個命令 extension（Rename/UpdateDescription/AddPermissions/RemovePermissions）：guard →（批次算淨效果）→ event → apply(event:)；Role+Delete.swift 只實作 when(event: RoleDeleted)（命令路徑走 repository.delete，見 Step 2）。

Step 2：Usecase 層

  1. RoleRepository：對照 EmployeeAccessRepository。
  2. CreateRole：name 非空 → Role(name:description:) → save → 回傳生成 roleId（唯一性檢查在 Adapter 層，見 §7 / Step 4）。
  3. RenameRole：find（nil → aggregateNotFound）→ rename → save（唯一性檢查同樣在 Adapter 層）。
  4. AddPermissions：整批 catalog 驗證 → find → addPermissions（淨空 → permissionsUnchanged）→ save。
  5. UpdateRoleDescription/RemovePermissions 同形；DeleteRole 走 repository.delete(byId:external:)——外部審查已確認其內部呼叫 markDelete() 並 emit DeletedEventType，不另寫 mark-delete 命令。

Step 3：Projector 層

GetRoles：read model id 固定 "all"；presenter 折疊 Created(append)/Renamed(改 name)/DescriptionUpdated(改 description)/Deleted(remove)。

fromStreams(["$ce-IAMRole"])
.when({
    $init: function(){ return {} },
    RoleCreated: link, RoleRenamed: link,
    RoleDescriptionUpdated: link, RoleDeleted: link,
});
function link(state, event) {
    if (!event.isJson) { return; }
    linkTo("IAM_GetRoles-all", event);
}

GetRoleHolders（EmployeeAccess 側，鏡像 PermissionHolders）：

fromStreams(["$ce-IAMEmployeeAccess"])
.when({
    $init: function(){ return {} },
    RolesAssigned: handleEvent, RolesRevoked: handleEvent,
});
function handleEvent(state, event) {
    if (!event.isJson) { return; }
    var roles = event.body["roles"];
    for (var i = 0; i < roles.length; i++) {
        linkTo("IAM_GetRoleHolders-" + roles[i], event);
    }
}

Step 4：Adapter 層

  1. RoleAggregate 8 個 ApplicationService（mutating 接 repository；CreateRole/RenameRole 另接 kdbClient——先查 GetRoles read model 做名稱唯一性 best-effort 再呼叫 Service；GetRoles 接 kdbClient；GetRolePermissions 接 repository）。
  2. EmployeeAccess 側 GetRoleHoldersApplicationService（接 kdbClient，空 → []）。
  3. 錯誤處理三段式：aggregateNotFound → 404；mapToApiError → 422；其餘 → 503。

Step 5：Server 掛載

IAMContextServer.swift 加一行 registerHandlers；gRPC services 陣列不動。

失敗路徑

  • createRole 空名稱：roleNameRequired → 422。可恢復。
  • create/rename 撞名：roleNameDuplicated → 422（best-effort，race window 見已知限制 #1）。
  • no-op（rename/description/批次淨空）：roleNameUnchanged/descriptionUnchanged/permissionsUnchanged → 422，UI 視為良性。
  • 操作不存在的 roleId：aggregateNotFound → 404。
  • 批次含 catalog 外權限：invalidPermission → 422，整批原子拒絕。
  • KurrentDB 不可用：503。不可恢復（infra）。
  • getRoles / getRoleHolders 而 projection 未部署：靜默回空 []，不是錯誤——部署是驗收前置步驟（已知限制 #2）。

不改動的部分

  • Sources/EmployeeAccessAggregate/ 中除改動表列出的三檔（openapi.yaml / projection-model.yaml / Adapter/ApiHandler.swift 的新增段落）與新增 GetRoleHolders 目錄外全部不動——特別是 Entity/、Usecase/Port/、Usecase/Service/、既有兩個 Projector、event.yaml、EmployeeAccessError.swift。
  • Sources/Generated/、proto/、gRPC PermissionsService 與 interceptor。
  • Sources/IAMPermissionCatalog/ 的各 context yaml（只讀 build 產物）。
  • AdminTokenMiddleware.swift、BearerTokenServerInterceptor.swift、既有 projections、scripts/projection.sh。

Non-goals（行為層）

  • 不包含員工有效權限合成——GET /employee-access/permissions/{userId} 與 gRPC 行為完全不變。
  • 不包含 assign-roles/revoke-roles 驗證升級（仍接受任意字串；但立下「傳 roleId」慣例）。
  • 不包含 role-holders 的 department/firm 過濾（permission-holders 有；v1 先不做）。
  • 不包含歷史 EmployeeAccess.roles 字串資料的遷移或對映。
  • 不包含前端 UI 與 per-role 細粒度授權（沿用 admin token 守門）。

已知限制

  1. 名稱唯一性 best-effort：read model 最終一致 ⇒ race window（create/rename）；嚴格唯一（reservation）defer。
  2. getRoles / getRoleHolders 最終一致：projection lag 數百 ms；未部署時回空清單而非錯誤——部署是上線前必要人工步驟。
  3. role holders 以字串原值分流：歷史資料若存名稱字串，用 roleId 反查不到；慣例自本 task 起 assign-roles 傳 roleId。刪除仍被持有的角色不阻擋、不影響有效權限；後續合成 task 以 fail-safe deny 處理（討論檔 D9）。
  4. no-op 回 422：UI 重送會看到 422，需視為良性。
  5. [inferred] 待實作首步驗證：PermissionCatalog 生成符號與 visibility；POST /roles 與 DELETE 動詞支援；event-generator-config.yaml 欄位形狀。（DDDKit delete 流程已由外部審查確認，移出 inferred。）
  6. 依賴關係：無前置 task。後續（不阻塞）：有效權限合成、assign-roles 驗證與歷史資料對映、role-holders 過濾、UI。
