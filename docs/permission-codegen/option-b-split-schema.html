PermissionKit · Schema 設計 · Option B

把 schema 拆成 permissions: + rules: 兩段

核心：把「有哪些權限（catalog）」和「哪條 route 要哪些權限（routing）」徹底拆開。一筆不再硬綁一條，於是「一個 endpoint 要多權限」「多個 endpoint 共用一條權限」都能自然表達。

0它解決什麼

現行 schema 是 fused 的：1 entry = 1 permission = 1 rule。表達不出兩件事：

  • GAP 1 — 一個 endpoint 需要多個權限（AND）：PermissionRule.requires 本來就是 [String]（AND 多權限），但 fused 每筆只能綁自己那一條。
  • GAP 2 — 多個 endpoint 共用同一條權限：fused 下每條 route 都鑄一條新權限，無法兩條 route 指向同一權限。
🎯

B 的做法：權限與規則各自獨立列，規則用「參照」指向權限 → rule 與 permission 變成多對多。

1Schema 對照

同樣的內容，左邊現行（fused）、右邊 B（split）。

現行 fused（1 entry = 1 perm + 1 rule）

context: OpportunityContext
serverPrefix: /opportunity-context
permissions:
  - slot: AuditQuoting
    operationId: editAccountingType
    method: patch      # 鑄權限 + 綁 route
    path: /audit-quotings/{id}/accounting-type

B split（catalog ⊥ routing）

context: OpportunityContext
serverPrefix: /opportunity-context

# ① catalog：有哪些權限
permissions:
  - { slot: AuditQuoting, operationId: editAccountingType }
  - { slot: AuditQuoting, operationId: approveQuote }
  - { slot: Workflow, operationId: closeDeal }

# ② rules：哪條 route 要哪些權限（用參照）
rules:
  # 1:1（最常見）
  - { method: patch, path: /audit-quotings/{id}/accounting-type,
      requires: [AuditQuoting.editAccountingType] }
  # GAP1：一條 route 需要多權限（AND）
  - { method: post, path: /audit-quotings/{id}/final-approve,
      requires: [AuditQuoting.approveQuote, Workflow.closeDeal] }
  # GAP2：兩條 route 共用同一權限
  - { method: post, path: /audit-quotings/{id}/close,
      requires: [Workflow.closeDeal] }
  - { method: post, path: /quoting-cases/{id}/close,
      requires: [Workflow.closeDeal] }

requires 用 <slot>.<operationId> 參照 catalog 的權限；generator 解析成 Permission.<const>.rawValue。

2關係：rules 與 permissions 變多對多

參照一拆開，兩個 gap 就只是「箭頭怎麼連」的自然結果。

➕

GAP1（AND 多權限）＝一條 rule 射出多支箭（final-approve → ApproveQuote ＋ CloseDeal）。

🔗

GAP2（共用）＝多條 rule 射向同一格（兩個 close → CloseDeal），不再各鑄新權限。

3產出（generator 怎麼吐）

permissions: → catalog 檔；rules: 解析參照 → 規則檔。

generated PermissionRules.swift（節錄，GAP1 那條）

PermissionRule(PathValidator(try Regex(#"/opportunity-context/audit-quotings/[^/]+/final-approve"#)),
    methods: [.post],
    requires: [Permission.auditQuotingApproveQuote.rawValue, Permission.workflowCloseDeal.rawValue]),

Permission.swift 與現行完全一樣（catalog 來自 permissions:）；差別只在規則檔的 requires 可以是多個、可以被多條 rule 指向同一個。

4驗證規則

  • Dangling ref = 編譯前就擋：requires 參照的權限必須在 permissions: 裡存在，否則 generator 報錯（拼錯/漏定義當場死）。
  • catalog-only 權限是合法的：某權限只在 permissions: 出現、沒有任何 rule 要求它 → 允許（例如要發布給 IAM 當 catalog、但本 context 沒有對應 route）。給 info 不報錯。
  • method / path：與現行一致（method 限 5 種、{param}→[^/]+）。

⚖️

唯一代價：最常見的 1:1 變囉嗦（同一個權限要在 catalog 寫一次、在 rules 參照一次）。若覺得痛，可加「rule 內可 inline 定義權限」的語法糖——但那會把 fusion 帶回來、削弱清晰度，建議先不做。

6遷移：parity 不破

B 是現行的超集。現行的 1:1 只是「每條 rule 剛好要求它自己那條權限」。

轉換後產出的 Permission.swift + PermissionRules.swift 與現行逐位元組可比、語意完全相同 → 既有 parity 測試照樣綠。

→我的立場

  • B 是長期正解：徹底解耦、兩個 gap 自然消失、沒有 Option A 那種「mint vs require 混在一筆 → orphan 權限」的語意疙瘩。
  • 但對方自評「目前用不到」（OC/IAM 全 1:1）。在沒有真實多權限 endpoint 之前就切 B，會讓最常見情況先承擔囉嗦，且 ref 形式、catalog-only 政策等細節缺真實案例校準。
  • 建議：先記 backlog，等第一個「一條 endpoint 要多權限」或「多 endpoint 共用」的真實需求出現，對著它一次切到 B（一步到位、parity 不破）。要現在就做也行——B 不會白做，是最終形狀。
