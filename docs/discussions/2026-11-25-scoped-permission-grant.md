# 權限帶範圍 討論摘要

## 背景

### 觸發的需求

OpportunityContext 的管理者看板要決定「誰能看、看到哪裡」（使用者 2026-11-25）：

| 誰 | 看到哪裡 |
|---|---|
| 所長張威珍、副所長施春成、張宏尉（未來的所長） | 全公司 |
| 分所長（台北楊大昀、桃園鍾政甫、台中吳珮瑜、彰化胡毓婷、嘉義張原瑄） | 自己的所 |
| 客服主管（總所劉雨珍、台北連德元、桃園鍾政甫、台中／彰化／嘉義吳珮瑜） | 負責的所（吳珮瑜一個人負責三個所） |
| 名冊職稱「組長」的人（漏掉的使用者之後處理） | 自己的組 |
| 組員 | 看不到 |

同一類需求還有：分配人員「負責哪些所的案件」、「可以把項目分到哪些所」，兩者不一定相同（使用者 2026-11-25）；歸屬「能歸屬哪些組的項目」（使用者 2026-11-26）。

使用者的原則（2026-11-26）：**用權限決定一個人能做的事，不看職稱，也不另外設「身分」**。系統裡不再有「組長」：一個人有沒有歸屬權限、能歸屬的範圍；有沒有看板權限、能看的範圍。

### 現況（正式版本）

- **正式環境全是直接授權**：在職有帳號 383 人；角色機制（`RoleAggregate`）與 console 角色頁做好了，但正式環境沒建過角色。
- **權限沒有範圍**：員工身上的 `firm`、`department` 是本人所屬，由管理者手動維護，跟 StaffContext 名冊沒有同步（`docs/tasks/2026-09-03-firm-format-and-scope-check.md`）。
- **組長機制**：OC 與 OpportunityPLForwarder 認組長＝「StaffContext 名冊同組 ∩ 持有 `OpportunityContext.Handover.AssignStaffMember`」。這個權限不守任何端點，但 OC 7 處、OpportunityPLForwarder 1 處靠它（見「第二階段」）。正式持有者是台中 7 人（審 1、3、5、6、7、8 的組長，加審 2 副理賴泳辰）。
- **分配用「一個所一個權限」**：`AllocateFor<所>`（某所的分配人員）、`AllocateTo<所>`（可分到某所）共 12 個，加上端點權限 `AssignDepartment`。正式只有吳岱芸持有（台中）。`AllocateFor` 後端沒有任何地方讀，只有 mendesky-web 選分配人員時拿來列候選（比對案件的報價單位）。
- **註記寫死「本人的組」**：9 支註記 API 都先查呼叫者今天在哪一組，那一組要有分到這家公司，否則 404；註記依組隔離。刪別人的註記要「組長 ∧ 有劃記權限」。正式 213 人有註記權限。
- **看板**：還在 OC、mendesky-web 的 `dev/managerDashboard` 分支，全所、所內、組內三個權限，所、組取操作者自己在名冊上的。
- **權限清單沒有「資料層」的結構化標記**：`[data-level]` 只寫在說明文字裡。
- **`grantPrivilege` 不檢查權限清單**；`EmployeeAccessAggregate` 刻意不依賴 `IAMPermissionCatalog`（`GetPermissionsApplicationService.swift:21-24`）。
- **授權只有人手**：寫入只來自 console、手動 curl、`scripts/grant-allocate-to.py`。
- **反查持有人慢**：IAM 列出某權限的全公司持有人要逐人重播時間軸；OC 認組長因此改成「先拿名冊組員、再問 IAM 這些人有沒有」（`permission-holder-check`）。
- **有些檢查只在 mendesky-web**：指定分配人員時被指定的人有沒有該所的 `AllocateFor`；每件案子的角色權限（只回給 web 決定按鈕，後端不執法）；指定、撤回分配人員時操作者跟這件案子的關係。

## 考慮過的做法

| | A. 權限帶所別 | B. 指派角色時帶範圍 | C. 範圍放 StaffContext | **D. 直接授權時帶範圍（選定）** |
|---|---|---|---|---|
| 吳珮瑜的看板 | 給「看板：台中」「…：彰化」「…：嘉義」三個權限 | 「分所長」「客服主管」兩個角色，客服主管的範圍選台中、彰化、嘉義 | IAM 給權限；StaffContext 記她管哪些所 | 給看板一次，範圍選台中、彰化、嘉義 |
| 數量 | 權限＝功能數 × 所數 | 角色照職務、範圍另選 | 同 D | 權限照功能、範圍另選 |
| 誰能做什麼記在 | IAM | IAM | IAM 與 StaffContext 兩處 | IAM |
| 正式環境轉換 | 不用 | 383 人全部改成角色 | 不用 | 不用；已有的歸屬、註記、分配權限補範圍 |

- **B 為什麼改掉**：排角色清單時改從人的角度看，發現職務角色多出來的是名字、不是內容（所長、副所長、所長特助、分所長、客服主管、組長六個角色裡都只有看板一個權限，差別只在範圍）；試行功能要另建「試行角色」；「同時是組長、又在試行分配才能歸屬」還要再建交集角色；383 人的轉換還要避開時間軸「撤銷不論來源」的陷阱。使用者決定先不處理角色。
- **C 不選**：StaffContext 審核主管設定（`ReviewerScope`）回答的是「這張報價給誰審」，表達不了跨所的客服主管，而且權限要兩邊一起看才完整。
- **D**：每個人身上就是「有哪些權限、範圍到哪裡」，console 員工頁一眼看完；沒有轉換。之後要做角色時，可以在 D 上再加「指派角色時帶範圍」（待決 4）。

## 決策

| # | 決策 | 狀態 |
|---|---|---|
| D1 | **先不做角色**：權限照現在直接授權給個人，正式環境不建角色、不轉換。角色的程式與 console 角色頁保留不動 | 使用者 2026-11-25 定 |
| D2 | **能做的事跟所、組有關，就帶範圍**：這次帶範圍的有看板、歸屬、分配、負責的所、看註記、刪別人的註記（見「各權限的範圍」）。報價審核級別不帶（D15）；訪談表管理、訪談表資料這次不處理（D16） | 使用者 2026-11-26 定 |
| D3 | **移除組長機制**：系統不再有「組長身分」。拿掉 `AssignStaffMember`；OC 與 OpportunityPLForwarder 裡依組長的判斷，全部改看歸屬權限與範圍（見「第二階段」） | 使用者 2026-11-26 定 |
| D4 | **分配合成一個權限；負責的所另一個**：`AssignDepartment`（能不能分配）與 6 個 `AllocateTo<所>`（能分到哪個所）功能重複——一定要一起給才有用——合成一個，沿用 `AssignDepartment`，範圍＝可分到的所。6 個 `AllocateFor<所>` 收成一個 `AllocateFor`，範圍＝負責的所；分配人員的資格比對案件的**報價單位** | 使用者 2026-11-26 定 |
| D5 | **權限與範圍一律在後端驗**：mendesky-web 只決定按鈕顯不顯示。現在只在 web 擋的（被指定的分配人員有沒有資格、指定與撤回分配人員時的關係）都要補到後端 | 使用者 2026-11-26 定 |
| D6 | **分三階段**：一、看板（新權限，沒有存量）；二、歸屬、註記、移除組長；三、分配。範圍的格式（D7～D9）在第一階段就定好 | 使用者 2026-11-26 同意 |
| D7 | **權限清單標「可選的範圍種類」**：範圍種類有全公司、指定所、指定組、本人的所、本人的組，每個權限只允許其中幾種（見「各權限的範圍」）。授權時選了不允許的種類就拒絕 | 使用者 2026-11-26 同意方向；每個權限的種類實作時再確認 |
| D8 | **範圍可以有多項，取聯集**：寫法參考 `ReviewerScope`：每一項是 `kind`（company／firms／departments／ownFirm／ownDepartment）＋清單，所別一律統編（`2026-09-03` 文件；IAM 檢查是 8 碼半形數字，不比對 StaffContext 的所別清單，2026-11-26），組存（所統編, 組名） | 使用者 2026-11-26 同意 |
| D9 | **範圍種類可以往後加**：`kind` 以字串存，解碼時不能因為不認得的種類而失敗；舊版讀到不認得的種類，只略過那一項 | 使用者 2026-11-26 同意 |
| D10 | **授權範圍化的權限時一定要帶範圍，沒帶就拒絕**；不是範圍化的權限帶了範圍也拒絕。讀取時，範圍化的權限沒有範圍，範圍查詢不列它。已經有人持有、之後才範圍化的權限，先幫這些人補範圍，各服務才改成看範圍（見「轉換順序」） | 使用者 2026-11-25 同意 |
| D11 | **「本人的所／組」在查詢當下由消費端用 StaffContext 名冊解析**，不用 IAM 自己存的 `firm`／`department` | 使用者 2026-11-25 同意 |
| D12 | **改範圍是另一個指令，用自己的事件型別 `PrivilegeScopeChanged`**：已持有的權限不能再授權一次（`permissionAlreadyExists`），所以改範圍用 `changeGrantScope { permission, scopes }`，發 `PrivilegeScopeChanged { userId, permission, grantScopes }`，如實記下「誰、什麼時候、把範圍改成什麼」，跟這個 aggregate 的調部門、升職一樣各有自己的事件。不用「撤銷＋授予」（會記一筆實際沒發生的撤銷；投影逐筆連結時中間可能查不到權限；兩筆時間各自取，重建時順序可能顛倒）。代價是新事件型別讓舊版 IAM fail-closed：上線後先不改範圍，等新版穩定、確定不退版再開始用（見「退版與部署」）。撤銷照現在「不論來源」，範圍一起拿掉 | 使用者 2026-11-26 定（取代 11-25「不新增事件型別」） |
| D13 | **角色裡不能放範圍化的權限**：角色加權限、指派角色時都擋；建立員工檔案的 API 不收權限（建檔指令一律從空權限開始）。不在 aggregate 的建構子加防護：那個建構子也用來重建舊資料，2026-06-22 以前的建檔事件帶有權限，加了會讓那些人讀不出來 | 使用者 2026-11-25 同意；建檔的寫法 2026-11-26 實作時更正 |
| D14 | **既有查詢不變；新增範圍查詢與反查**：`getPermissions` 照舊只回權限字串；範圍不能編進權限字串（各處都是字串完全比對）。新增「權限＋範圍」查詢（第一階段）。第二階段起要反查「誰的歸屬範圍涵蓋某組」「誰的負責的所涵蓋某所」：全公司、指定所、指定組這些寫死的範圍，由 IAM 建一份「權限 → 人和範圍」的讀模型直接查；本人的所、組，從名冊成員找、再問 IAM 這些人的範圍 | 使用者 2026-11-26 同意方向 |
| D15 | **報價審核不改**：一級、二級照常直接授權、不帶範圍；誰審誰留在 StaffContext 審核主管設定（業務是指定一位主管審） | 使用者 2026-11-26 定 |
| D16 | **這次不處理**：訪談表管理（還沒上線）、訪談表資料（查詢訪談表、各卡片讀寫、電子發票密碼、AuditContext／EvidencePurchaseContext 客戶資料）照現在的行為 | 使用者 2026-11-26 定 |

### 各權限的範圍

| 權限 | rawValue | 範圍的意思 | 可選的範圍（建議） | 階段 | 要給／補範圍的人 |
|---|---|---|---|---|---|
| 看板 | 新（取代分支上三個） | 看得到哪些所、組的案件（依負責人） | 五種都可以 | 一 | 32 人新給（下表） |
| 歸屬 | `Handover.EditBelongedMember` | 能歸屬哪些組的項目 | 本人的組、指定組、本人的所、指定所 | 二 | 台中 7 人：本人的組；吳岱芸：指定所「台中」（＝台中所有的組） |
| 看註記 | `Annotating.GetAnnotations` | 能看、能寫哪些組的註記 | 五種都可以 | 二 | 現有 213 人：本人的組 |
| 刪別人的註記 | 新 | 能刪哪些組裡別人的劃記、留言 | 五種都可以 | 二 | 台中 7 人：本人的組（現在能刪的就是他們） |
| 分配 | `Handover.AssignDepartment`（併入 6 個 `AllocateTo<所>`） | 能把項目分到哪些所 | 全公司、本人的所、指定所 | 三 | 吳岱芸：指定所「台中」 |
| 負責的所 | `Handover.AllocateFor`（6 個收成 1 個） | 能當哪些所的案件的分配人員（比對案件的報價單位） | 本人的所、指定所 | 三 | 吳岱芸：指定所「台中」 |

範圍是「所」時，涵蓋那個所所有的組，之後新增或改名的組也自動涵蓋；只有要涵蓋「某所的部分組」時才逐一選指定組（組改名、拆併後要重設，見待決 1）。

註記其他權限（劃記、留言、編輯、刪除自己的）不帶範圍，只決定能做哪個動作；能在哪幾組做，跟著「看註記」的範圍（待決 3）。

### 報價審核為什麼不改（D15）

- 業務是「指定一位主管審」：每層一位預設、可以有候選、越細越優先（個人＞組＞所＞全公司＞自動推導）、排除送審者本人、個人層的例外（王紅晴、許景存、劉雨珍本人給邱藍儀審）。這是「送給誰」的流程規則，StaffContext 審核主管設定已經做好（StaffContext #42）。
- IAM 範圍適合的是「範圍內的主管誰都可以審」，還要多一種「指定人」範圍、能排除個人。
- 不兩邊都做（IAM 管誰可以審、StaffContext 管預設送誰），以免同一件事兩處維護。
- 讀審核級別的地方都只比對權限字串，範圍化不影響審核。
- 兩邊要對得上：StaffContext 選候選人時不看 IAM 權限。上線時授權和審核主管設定用同一份名單。

## 設計

命名先避開 IAM 已有的 `scope`（`scope-check`、`PermissionScopeFilter` 指的是持有人自己的所、組）。下面用「授權範圍」`grantScope`，實作時再定。

### 權限清單

- 每筆權限加選填欄位 `grantScopeKinds: [...]`（沒寫＝不是範圍化的權限）。寫在權限所屬 context 的權威 yaml（這次都在 OC 的 `OpportunityContext.permissions.yaml`），IAM 的 `IAMPermissionCatalog` 逐字複本跟著。
- 舊版解析器遇到不認得的 key 會略過；`PermissionCatalogEntry` 的欄位一定要是選填。
- IAM 的 `PermissionCatalogEmitter` 另外產出「範圍化的權限 → 可選種類」，給授權、改範圍、角色加權限、指派角色的檢查用。`EmployeeAccessAggregate` 要能讀到這份清單（加依賴 `IAMPermissionCatalog`，或在 server 組裝時注入）。

### EmployeeAccess

- `grantPrivilege` 的輸入加選填 `grantScopes`（權限 → 範圍清單）。`PrivilegeGranted` 事件加同名欄位，**一定要是 Optional**：非 Optional 的話舊事件解不開，aggregate 讀取會略過那筆（權限默默消失），時間軸整個 503。
- 新指令 `changeGrantScope { permission, scopes }`：權限要是直接持有、目前有效（直接授予後可能因撤銷含它的角色而失效）、而且是範圍化的權限；範圍跟現在一樣回 `grantScopeUnchanged`；發 `PrivilegeScopeChanged { userId, permission, grantScopes }`。轉換時幫已持有、還沒有範圍的人補範圍，也用這個指令。
- 檢查（D7、D10、D13）：範圍化的權限每個都要有至少一項範圍、種類要在允許的清單裡；不是範圍化的權限不能有範圍；範圍內容要合法（指定所至少一個、所別是 8 碼統編、指定組要所＋組）。

### 有效權限重播

狀態從「權限集合」改成「權限 → 範圍清單（範圍化的才有）」：授予時記下範圍；撤銷（不論來源）連範圍一起拿掉；改範圍（`PrivilegeScopeChanged`）在權限仍有效時換範圍、不改有效權限；建立員工檔案、角色相關事件照現在（不會帶進範圍化的權限）。`getPermissions` 回的權限字串跟現在完全一樣。

## 退版與部署

- **授權帶範圍可以退版**：範圍放在 `PrivilegeGranted` 的選填欄位。舊版 IAM 用編譯器合成的 Decodable 解事件，多出來的欄位會略過，所以只用到授權帶範圍時可以退回正式現在的 1.8.0；退版期間範圍查詢不存在，範圍化的權限會被當成一般權限。退版期間如果有人授了範圍化的權限但沒帶範圍，回到新版後要補範圍。
- **改範圍是新事件型別（D12），寫過之後不能退回 1.8.0**：舊版讀到 `PrivilegeScopeChanged` 會 fail-closed，那個人在各服務的查權限都會失敗。所以新版上線後先不改範圍，等新版穩定、確定不會退版再開始用。第一階段看板只需要授權帶範圍；改範圍最早在第二階段補範圍時才需要。
- **範圍種類往後加也不能壞**（D9）。
- **投影**：`IAM_GetPermissions` 要多連結 `PrivilegeScopeChanged`。部署方式：停用 → 換查詢（`PUT /projection/IAM_GetPermissions/query?type=js&emit=true`）→ 啟用，進度保留、不重建；這個型別上線前沒有任何歷史事件，不用 reset（2026-11-26 在本機測試庫 2117 演練過）。不能用 `scripts/projection.sh`（先刪再建，重建期間全員 403）。IAM 的 `GetPermissions` 讀取模型也要列入這個事件（no-op），否則 DDDKit presenter 遇到沒列名的事件會中止整段重播。`IAM_PermissionHolders` 只看授予與撤銷，不用改。第二階段的反查讀模型是新的投影，新建不影響既有的。
- 不用角色，「時間軸合併員工與角色事件，要在 KurrentDB 26.1 跑整合測試 #24」不再是這次的前置。
