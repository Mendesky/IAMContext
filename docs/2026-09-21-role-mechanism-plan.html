角色機制規劃

讓角色成為權限的定義主體，並讓「改角色」等於「改所有持有者的有效權限」，而且不對任何一位員工寫入事件。

一結論

  1. 沿用既有規格，解除一條範圍外。2026-08-06 已有一份通過審查的 Role aggregate 規格（docs/tasks/role-aggregate.md，狀態 ready、尚未實作）。它明確把「員工有效權限＝直接授權 ∪ 角色展開」列為不做；本輪把這一條做進來。
  2. 同步機制推薦「引用＋查詢時合成」。員工只存 roleId，權限清單只存在 Role。查權限時把兩邊合起來。角色一改，下一次查詢就是新結果，不需要對任何持有者發 command。
  3. 命名調整兩處。指派角色不落在 Role，沿用 EmployeeAccess 既有的 assignRoles／revokeRoles，補上「roleId 必須存在」的驗證。加減權限拿掉 InRole／FromRole 後綴，改成 addPermissions／removePermissions。
  4. 分三階段交付。階段一角色本體，階段二合成（本輪重點：getPermissions 與 permission-holders 反查兩個讀取端同時切換），階段三管理視圖與清理。gRPC 契約（proto）三個階段都不變。
  5. 消費端已有 60 秒快取，角色不會讓它更糟。Middleware 的 CachingPermissionsProvider 讓權限變更最多延遲 60 秒生效，今天的直接授權與收回已是如此。角色編輯走同一條路，不需要為它加通知層。

二現況：為什麼角色現在沒有作用

角色在 IAMContext 裡目前只是掛在員工身上的字串標籤。沒有定義主體，也不參與權限計算。

四邊界：兩個 aggregate 各守一個事實

Role 回答「這個角色是什麼」：名稱、描述、權限集合。EmployeeAccess 回答「這位員工持有什麼」：直接授權的權限，加上持有的 roleId。兩者之間沒有需要同時成立的不變式，關聯只在讀取時合成。這是整個設計的基礎，第五節的同步機制直接從這裡推出來。

五核心：角色權限變更如何同步到持有者

你點出的問題有三種解法。差別在「角色改一次，系統要做多少事」以及「權限來源會不會混在一起」。

方案做法角色改一次的成本一致性主要風險
A　複製展開 指派時把角色的權限複製進員工的 permissions。角色改動後，由 process manager 查出持有者，逐一對每人發 grant／revoke。 N 個 command、N 個事件，N＝持有人數。 最終一致，且可能半途失敗，留下一半人已更新的狀態。 必須標記每個權限的來源，否則從角色移除某權限會誤刪剛好也被直接授予的人。角色編輯與同時進行的指派有競態。員工的事件流被機械事件淹沒，審計價值下降。
B　引用＋查詢時合成推薦 員工只存 roleId。查詢時計算 直接授權 ∪ ⋃ role.permissions。 1 個事件（例如 RolePermissionsRemoved）。與持有人數無關。 角色部分強一致（每次查詢 rehydrate Role）。指派部分維持既有 projection 的延遲。 getPermissions 多 K 次 Role 讀取，K＝該員工的角色數，通常個位數。「誰持有某權限」的反查要改成聯集（第九節階段三）。
C　B＋變更通知 同 B，另在角色變更時發整合事件或推播，讓消費端失效快取。 1 個事件＋1 次通知。 同 B。 消費端確實有快取（見下方「消費端生效延遲」），但那個延遲今天對直接授權同樣存在。為角色單獨加通知層，會讓兩種來源的生效時間不一致，反而難解釋。不建議本輪做。

推薦 B 的理由

  1. 每個事實只有一個寫入點。權限清單在 Role，持有關係在 EmployeeAccess。方案 A 讓同一份清單在 N 條 stream 各存一份，之後每次區分「角色來的」與「直接給的」都要靠額外標記維持。
  2. 角色編輯是常數成本。一個角色被 3 個人或 300 個人持有，改起來都一樣，不會產生事件風暴。
  3. 直接授權與角色展開天然分離。從角色移除某權限，不會動到剛好也被直接授予同一權限的人；撤銷角色也不會刪掉直接授權。這不是額外邏輯，是結構的結果。
  4. 刪除角色的語意自然成立。roleId 解析不到就貢獻零權限，正是既有裁決 D9 的 fail-safe deny。
  5. 符合事件溯源的分工。aggregate 守寫入不變式，「有效權限」是衍生的讀取視圖。這也是舊討論 L28 當年猶豫的點，現在把它接起來。

落地位置

  • 在 EmployeeAccessAggregate 新增 protocol RoleDirectory，一個 port 兩個用途：resolve(roleIds:) 回傳「roleId → 權限集合」的字典，查不到或已刪除的 roleId 不出現在結果裡。getPermissions 用它取權限做聯集；AssignRolesService 用它驗證每個 roleId 都有出現，缺一個就拒絕。adapter 由 RoleAggregate 的 repository 實作，EmployeeAccessAggregate target 不依賴 RoleAggregate target，整合測試可注入假的目錄。
  • 注入點有兩個，必須同時改。HTTP 的 ApiHandler 目前在 EmployeeAccessAggregate 內部自行建立 GetPermissionsApplicationService（Sources/EmployeeAccessAggregate/Adapter/ApiHandler.swift），gRPC 的 PermissionsService 也各自建立一份（Sources/IAMContextServer/PermissionsService.swift）。兩者都改成從初始化參數接收 RoleDirectory，由 IAMContextServer 組裝時傳入同一個實例。只改其中一邊，另一邊就不會展開角色。
  • GetPermissionsPresenter 開始折疊 RolesAssigned／RolesRevoked 到 read model 的 roles 欄位。目前這兩個事件是 no-op。
  • GetPermissionsApplicationService 在折疊完後呼叫 RoleDirectory，回傳 permissions ∪ ⋃ resolve(roles).values。解析不到或已刪除的 roleId 自然不在字典裡，直接略過。
  • 解析方式用 Role aggregate rehydrate，每個 roleId 一次 stream 讀取。角色部分因此是強一致：改完角色的下一個查詢就生效。角色數量成長到需要時，再改為折疊 $ce-IAMRole 的單一目錄 stream（既有規格 getRoles 用的 projection）並加短 TTL 快取。那是效能優化，不是設計改變。
  • HTTP GET /employee-access/permissions/{userId} 與 gRPC getPermissions 用同一個 application service 類別，但各自建立實例。兩個入口都注入 RoleDirectory 後才算兩邊同時生效。proto 不變，消費端不需改碼。

消費端生效延遲

IAM 這一端改完角色，下一個查詢就是新結果。但消費端不是每個 request 都來問。Middleware 套件的 CachingPermissionsProvider 是每個 process 內的 TTL 快取，正權限預設 60 秒、空結果 10 秒，有 invalidate 介面但目前沒有任何呼叫點。AuditContext 的 composition root 已經用它包住 gRPC client。

這表示今天一筆直接授權被收回，持有者最多還能再用 60 秒。角色編輯的生效延遲與此完全相同，只是一次影響的人數更多。若業務上需要更快的收回，該修的是快取層（縮短 TTL，或由 IAM 廣播失效），而且要對直接授權與角色一起修。這是獨立於角色機制的題目，本報告不納入。

八與既有規格的差異

  • 解除 Non-goal 第一、二條。有效權限合成與 assign-roles 驗證納入階段二。
  • 回歸保護縮小適用範圍。既有規格要求「EmployeeAccess 核心區塊 git diff --stat 必須為空」，只適用階段一。階段二明確改動 GetPermissionsPresenter、GetPermissionsApplicationService、AssignRolesService 三個檔。
  • 新增介面。RoleDirectory port、RoleAggregate 端的 adapter，以及 ApiHandler／PermissionsService 初始化參數的變更，都是既有規格沒有的。
  • getRoles 的 read model 多帶 permissions。既有規格只回 roleId、name、description。反查要找「含某權限的角色」，必須在同一個折疊裡帶上權限集合。
  • 反查跟著切換。getPermissionHolders 改為聯集，與 getPermissions 同一階段上線。原因是 OpportunityContext 後端與 mendesky-web 的選派人 modal 都吃這個端點：若只切 getPermissions，會出現「有權限卻選不到人」的不一致。
  • 新增查詢。階段三的 getEffectivePermissions 明細與懸空 roleId 清理，既有規格沒有。
  • 其餘照舊。六個 command、六個 event、三個查詢、D1–D16 全部沿用。registry 狀態要從 ready 改回 draft，走一次 update-spec 回填後再審。

九實作階段與驗收

三個階段有先後依賴：沒有 Role 就沒東西可以合成，沒有合成就沒東西可以反查。

  1. 角色本體

    照既有規格實作，getPermissions 行為在這一階段完全不變。

    • 新 target RoleAggregate：Package.swift 宣告（比照 EmployeeAccessAggregate 的 plugins 與 resources）、IAMContextServer 註冊 ApiHandler、IAMContextTests 加依賴。
    • .ai/contexts/IAMContext/Role/ 補 commands、invariants、errors、api、test-scenarios 五份 SSOT。
    • projection：IAM_GetRolesProjection.js、IAM_RoleHoldersProjection.js，並加進 scripts/projection.sh。getRoles 的 presenter 一併折疊 RolePermissionsAdded／Removed（第八節）。
    • 驗收：swift build 綠；RoleIntegrationTests 綠；EmployeeAccess 核心區塊 diff 為空。

  2. 合成 本輪重點

    角色開始影響有效權限。兩個讀取端同一版切換。切換前先確認每個消費端的權限 catalog 都已登錄（workspace 鐵則 3）。

    • RoleDirectory port ＋ RoleAggregate 端 adapter；ApiHandler 與 PermissionsService 改為注入；Presenter 折疊 roles；AssignRolesService 經 RoleDirectory 驗證 roleId。
    • getPermissionHolders 改為聯集：直接持有者 ∪ 含該權限之角色的持有者。用 getRoles 目錄（已帶 permissions）找出含該權限的角色，再用 getRoleHolders 取持有者；既有的 department／firm 過濾套用在聯集後的結果上。成本界線：過濾是逐人讀 read model，今天的直接持有者路徑已是如此（Sources/EmployeeAccessAggregate/Adapter/GetPermissionHolders/GetPermissionHoldersApplicationService.swift）；聯集後人數上限是全公司員工數，數百人，可接受。若日後要更快，再加一支帶部門欄位的 role-holders projection，不改設計。
    • 驗收測試（swift-testing，接真實 KurrentDB，沿用 Tests/IAMContextTests/IntegrationTestSupport.swift 的 seedActiveProfile）：
      • createRole → addPermissions → assignRoles → HTTP GET /employee-access/permissions/{userId} 與 gRPC PermissionsService.getPermissions 都含該權限。
      • 兩位以上員工持有同一角色，removePermissions 後兩個入口立即都不含該權限，不重啟、不等待；且 $ce-IAMEmployeeAccess 類別 stream 的事件數在角色編輯前後完全相同，證明對任何持有者都沒有扇出。
      • deleteRole 後該角色權限消失，直接授權仍在。
      • 直接授權與角色給同一權限，從角色移除後仍有效。
      • 兩個角色含同一權限，移除其一仍有效。
      • assignRoles 帶未知 roleId 被拒絕。
      • 手動寫入舊字串的 RolesAssigned，getPermissions 不報錯、不多出權限。
      • 注入假的 RoleDirectory 時，HTTP 與 gRPC 兩個入口都使用該假目錄，證明兩個注入點都接上。
      • 某人只經由角色持有權限 p，getPermissionHolders(p) 列出他；從角色移除 p 後不再列出；帶 department 過濾時結果一致。

  3. 管理視圖與清理

    讓管理者看得到「為什麼這個人有這個權限」。

    • getEffectivePermissions：回傳直接授權與每個角色各貢獻的權限。
    • 懸空 roleId 清理查詢。
